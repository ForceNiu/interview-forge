# AI 自动出题 · 提示词（Prompt）设计与方案说明

> 本文档对应代码：`src/lib/ai/workflow.ts`（工作流编排）与 `src/lib/validator.ts`（确定性校验）。
> AI 自动出题（AI 出题）由 LangGraph 编排的 5 节点工作流（Workflow）完成，其中 **3 个节点调 LLM（大模型）生成内容**，它们的"提示词"是这套系统的核心。本文档逐段介绍这三段提示词，并说明背后的设计决策。
> 📌 本文聚焦「三段提示词的原文 + 设计决策」；端到端控制流图见姊妹文档 [AI工作流-流程图总览](AI工作流-流程图总览.md)。

---

## 一、提示词全景：哪几个节点用了 Prompt（提示词）

| 节点 | 名称 | 是否调 LLM | 提示词作用 |
| --- | --- | --- | --- |
| ① | analyzeResume（分析简历） | ✅ 是 | 把简历文本结构化，提取技能 / 水平 / 盲区，作为后续所有节点的"单一事实来源（single source of truth）" |
| ② | routeCandidate（路由分流） | ❌ 否 | **确定性纯函数**，不调 LLM——算出候选人水平 / 目标角色 / 题型权重 |
| ③ | planStrategy（规划策略） | ✅ 是 | 依据分析结果 + 路由决策，决定"出哪些域、各几道、什么题型" |
| ④ | generateQuestions（生成题目） | ✅ 是 | 按策略为每个知识域生成具体题目（含 3 种题型模板） |
| ⑤ | validateQuestions（语义校验） | ❌ 否 | **确定性规则**，对每题做客观检查，不达标域进入"重出"队列 |

**关键结论**：LLM 只负责"理解语义 / 生成自然语言"，而"路由、校验、重试"这些需要可控、可复现的环节，全部拿回确定性代码——这是整套提示词设计的底层哲学（详见第四节）。

## 二、提示词逐段介绍

### 2.1 节点① 分析简历（analyzeResume）

- **Persona（角色设定）**：`你是一位资深前端面试官`
- **输入**：候选人简历文本；若提供了 JD（Job Description，职位描述），追加"对比 JD 要求与简历差距，标注为 blindSpots（盲区）"。
- **输出**：一段纯 JSON（不要其他文字），字段如下：

  ```json
  {
    "primaryStack": "主要技术栈",
    "skills": ["技能1", "技能2"],
    "skillCategoryMap": { "vue": ["Vue3", "Pinia"], "engineering": ["Webpack", "Vite"] },
    "domainDepth": { "vue": "deep|medium|gap", "css": "deep|medium|gap", "...": "..." },
    "projects": [{ "name": "项目名", "tech": ["技术"], "depth": "deep|medium" }],
    "overallLevel": "junior|mid|senior|staff",
    "highlights": ["最值得深挖的 2-3 个亮点"],
    "blindSpots": ["该级别应掌握但简历未体现的知识点"]
  }
  ```

- **关键指令（提示词原文要点）**：
  - 知识域分类固定为 **10 个域**（见 2.4 节 `SKILL_CATEGORIES`），要求"按知识域精准归类，同一技能不跨类"。
  - depth（深度）判断规则：项目有量化成果 / 具体技术细节 / 踩坑复盘 → `deep`；仅简单提及技术栈 → `medium`。
  - blindSpots（盲区）规则：对比前端知识域分类与该级别期望，找出缺失（例：senior 没提性能优化 → 标记盲区）。
  - **domainDepth 自洽性约束**：highlights 提到的域必须是 `deep`，blindSpots 提到的域必须是 `gap`，`deep` 项目覆盖的域不能低于 `deep`，技能为空的域不能标 `deep`。
  - 明确红线：`只列出简历中真实出现的技能，不要编造简历里不存在的内容；识别不到就写空数组，不要硬凑`。

- **设计点**：这段输出是后续 ③ ④ ⑤ 的"单一事实来源"——下游节点不再重新读简历，只消费这份结构化结果，保证全链路口径一致、可复现。

### 2.2 节点③ 规划策略（planStrategy）

- **Persona（角色设定）**：`你是一位有10年经验的前端 Tech Lead 面试官`
- **输入**：① 的分析结果 + ② 的路由决策（以 `routingHint` 注入，含候选人水平 / 目标角色 / 题型权重建议）+ `depthSummary`（每个域 deep/medium/gap 标记）。
- **输出**：一段纯 JSON（不要其他文字），`domains[]` 数组，每个域含：

  ```json
  {
    "name": "知识域名称",
    "category": "js-basic|css|browser|vue|react|engineering|network|performance|electron|typescript",
    "depth": "deep|medium|gap",
    "questionType": "project-deep-dive|concept|gap-fill",
    "count": 1,
    "reasoning": "为什么选这个域和题型，属于三层追问框架的哪一层"
  }
  ```

- **关键指令（提示词原文要点）**：
  - **三层追问框架 + 确定性映射**：`domainDepth` 严格映射到题型，LLM 不做自由裁量——
    - `deep` → `project-deep-dive`（第三层：实战追问）
    - `medium` → `concept`（第一/二层：基础概念 + 原理深挖）
    - `gap` → `gap-fill`（补缺题）
  - 总量约束：`总共生成 8-10 道题，至少覆盖 2 个不同的知识域分类`。
  - 难度递进：`concept → gap-fill → project-deep-dive`（由易到难）。
  - 有盲区且 `hasBlindSpots` 为 true 时，`gap` 域至少一道补缺题。

- **设计点**：LLM 在这里只做"按映射填表 + 写 reasoning（推理说明）"，**不行使自由裁量权**——出几道、什么题型，由确定性映射定死，LLM 负责把"为什么"讲清楚。

### 2.3 节点④ 生成题目（generateQuestions）

- **Persona（角色设定）**：`你是一位有10年经验的前端 Tech Lead 面试官`
- **三种题型模板（questionTemplate，按 questionType 切换）**：
  - `project-deep-dive`（实战追问）→ **STAR 框架**（来自 bq-skill 行为面试技能）：
    `开场描述具体场景/挑战（Situation & Task）→ 追问行动与方案选择（Action）→ 深挖效果与改进（Result）→ 如果重设计会怎么做；难度 4-5，含多个子问题`。
  - `gap-fill`（补缺基础）→ 基础概念型（来自 mock-interview 技能的"第一层：基础概念"）：
    `考察核心概念和基本原理，用"说说你对 XX 的理解"这类开放句式，而非判断题；难度 2-3`。
  - `concept`（概念深挖）→ 第一层 + 第二层（来自 mock-interview 技能）：
    `第一层开放式问题确认基本理解 → 第二层预留追问空间（"请进一步说明…""与 XX 相比有什么区别？"）；难度 3-4`。
- **主提示词输出**：一段纯 JSON 数组（不要其他文字），每题含：

  ```json
  [
    {
      "title": "题目（一句话，尽量用开放式问法）",
      "content": "详细题目内容（含上下文 / 具体场景 / 追问子问题）",
      "difficulty": "数字 1-5",
      "tags": ["知识域标签1", "知识域标签2"]
    }
  ]
  ```

- **重要提醒（提示词原文要点，来自 mock-interview 经验）**：
  - 题目应是**开放式**的，引导展开回答，而非简单是非题。
  - `project-deep-dive` 要包含具体场景，让候选人讲真实项目经历。
  - 标签用前端行业常用术语（如"Vue3 响应式原理""Webpack Tree Shaking""浏览器渲染管线"）。
  - 内容可含 2-3 个引导性子问题，模拟真实面试追问节奏。

- **设计点**：题型模板把"面试方法论"直接固化进提示词——STAR、概念分层、开放句式都不是模型临时发挥，而是显式写死的结构。

## 三、设计方案说明（为什么这么设计）

### 3.1 LLM 与确定性代码的分工

这是整套设计的第一性原理。5 个节点里，**② 路由分流**和 **⑤ 语义校验**刻意不用 LLM：

- **节点② 路由分流**是纯函数 `computeRouting`：输入 ① 的结构化分析，输出水平 / 目标角色 / 题型权重。注释明确写道——"输入已是结构化对象、需要同输入必同输出（可控可复现）、省一次 token（大模型计费单位）往返、且避免 LLM 分类漂移 / 幻觉"。
- **节点⑤ 语义校验**是确定性规则 `validateQuestionSemantics`：对每题做客观检查（详见 3.7 节），不靠 LLM 自评。

本质一句话：**把需可控的环节从 LLM 手里拿回确定性代码**。LLM 只用在"真的需要理解语义 / 生成自然语言"的 ①③④ 三处。

### 3.2 知识域分类体系（10 个固定域）

`SKILL_CATEGORIES` 常量定义了一套贯穿全链路的统一语言：

```
js-basic（JS 基础）· css · browser（浏览器）· vue · react · engineering（工程化）
network（网络）· performance（性能优化）· electron · typescript
```

它同时出现在 **① 的分类输出、③ 的 category 取值、④ 的标签、⑤ 的校验上下文** 中。统一 taxonomy（分类法）的好处：分析、规划、出题、校验四阶段说"同一种话"，不会出现"分析说 Vue、出题说框架"的错位。

### 3.3 三层追问框架 + 确定性映射

面试不是"随机出题"，而要有难度递进。设计上把题目分成三层：

| 层 | 名称 | 对应 questionType | 题型模板来源 |
| --- | --- | --- | --- |
| 第一层 | 基础概念 | `concept`（部分） | mock-interview 技能"第一层" |
| 第二层 | 原理深挖 | `concept`（部分） | mock-interview 技能"第二层" |
| 第三层 | 实战追问 | `project-deep-dive` | bq-skill 的 STAR 框架 |

**确定性映射**是这套设计的关键护栏：`domainDepth`（来自 ① 对简历的判断）→ 直接决定 `(depth, questionType)`。LLM 不能在"出几道、什么题型"上自由发挥，只能按映射填表——既保证覆盖面与难度递进，又避免模型偷懒全出简单题。

### 3.4 Persona（角色）分层

提示词用了两套面试官角色，对应不同职责：

- **① 分析简历** → `资深前端面试官`：扮演"读懂简历的人"，侧重提取与归类。
- **③ ④ 规划 / 出题** → `有10年经验的前端 Tech Lead 面试官`：扮演"会追问原理与项目、能判断深度的决策者"。10 年经验这个设定，暗示模型应倾向于深挖原理、结合真实项目场景，而非停留在定义层面。

### 3.5 结构化 JSON + Zod 校验 + 错误回灌（自我优化闭环）

每个 LLM 节点都被要求"只输出纯 JSON（不要其他文字）"，原因是有确定的下游消费方：

1. **Zod（类型校验库）解析**：节点①用 `analysisSchema`、节点③用 `strategySchema`、节点④用 `generatedQuestionSchema` 解析模型输出。
2. **畸形 / 不达标 → 抛错 → 回灌**：节点①③④都有手写 `for` 循环重试（最多 `MAX_ATTEMPTS=3` 次）。失败时把错误原文（`lastErr` / `extraHint`）拼回提示词尾部，让模型"看到自己上次错在哪"再修正——例如节点③会把"出题策略总量校验失败：应 8-10 题"直接回灌。
3. **精炼环（refine loop）**：节点⑤发现不达标域 → 条件边回 ④ **只重出失败域**，并注入"上一版该题未通过质量校验，请重点改进——确保开放式问法、与候选人技术栈相关、内容 30 字以上、带标签"。这就是"自我优化"的实质：好题保留（不连坐），只换坏桶，且每轮都更聪明。
4. **硬上限**：精炼环最多 `MAX_REFINE_ROUNDS=2` 轮，保证必终止（不撞 Vercel 300s 部署超时）。

> 之所以**手写重试**而非交给 LangGraph 框架的 `retryPolicy`：框架用相同入参重跑整个节点，模型会重复同一个错误（真实简历必卡在 domainDepth 自洽校验），且会把已成功的域也连坐重跑。手写回灌 + 域级重试解决了这两个问题。

### 3.6 Skill（技能）经验注入

提示词不是凭空写的，而是把已验证的面试出题方法论直接固化进去：

- **mock-interview 技能**（前端八股文面试）：贡献了"三层追问 / 开放句式 / 概念 vs 原理分层"等指令，节点①③④的提示词多处标注"来自 mock-interview skill 的经验"。
- **bq-skill 技能**（行为面试 STAR 框架）：贡献了 `project-deep-dive` 题型的 STAR 结构（Situation → Action → Result → 复盘）。

设计意图：让 LLM 出题"像一位真面试官在按方法论出题"，而不是发散地生成。

### 3.7 JD（职位描述）感知

若用户提供了目标岗位 JD，两处会联动：

- 节点①追加：对比 JD 要求与简历内容的差距，把缺失点标记进 `blindSpots`。
- 节点③提示词追加：`请同时考虑 JD 要求但简历中缺失的技能作为 gap 域`。

效果：出的题既贴合候选人真实经历，又对准投递岗位的缺口。

### 3.8 工程护栏（并发 / 超时 / 重试）

- **5 路并发**：各知识域互相独立，用 `mapWithConcurrency(limit=5)` 并发调 LLM。实测 DeepSeek 在 5 路下零 429 且提速最优（≈3.8x），10 路仍零 429 但收益递减。
- **单次调用超时**：`NODE_TIMEOUT_MS=300000`（300 秒）墙钟上限，超时即中止并触发重试。
- **调用层失败重试**：每个域调用失败重试最多 3 次；仍失败则标记 `callFailedDomains` 并**跳过该域**（不阻断整体出题），且不再进精炼环避免死循环。
- **域级重试（不连坐）**：只重跑失败域，已成功的域保留。

## 四、校验规则速查

确定性校验是"提示词设计"的守门员，分三处：

| 校验点 | 位置 | 规则 |
| --- | --- | --- |
| 节点⑤ 语义校验（每题） | `validateQuestionSemantics` | ① 难度在 1-5；② 内容 ≥ 30 字；③ 至少一个标签；④ 含开放式问法（为什么/如何/说说/怎么/区别/对比/解释/设计/什么/哪些/怎样）；⑤ 与候选人简历或技能有词重叠（相关性） |
| 节点① 自洽校验 | `validateDomainDepthConsistency` | ① 亮点域必 `deep`；② `deep` 项目覆盖的域不能低于 `deep`；③ 技能缺口域必 `gap`；④ 技能为空的域不能标 `deep` |
| 节点③ 总量校验 | `validateTotalCount` | 所有域 count 总和必须在 **8-10** 范围内 |

> 前两条校验的违规信息，会作为"上一版为何不达标"回灌给节点④，驱动精炼环自我修正（见 3.5 节）。

## 五、一句话总结

这套自动出题的提示词设计，核心不是"写好一段神 prompt（提示词）"，而是**用确定性代码搭好骨架（10 域分类、三层映射、路由与校验），让 LLM 只在"理解简历"和"按框架生成自然语言题目"两件事上发挥**——既可控可复现，又借 STAR / 概念分层等面试方法论保证出题质量。

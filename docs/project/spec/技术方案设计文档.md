## 1. 设计目标与约束

### 1.1 设计目标
- 用**可编排、可观测、可控**的方式实现「基于简历的定制化 AI 出题」，而非一次性 prompt（提示词）拼接。
- 把「需要确定性」的环节（路由、质量校验）从 LLM 手里拿回代码，保证**可复现、可调试**。
- 提供**四层可观测性**，使每一次出题运行都可复盘。

### 1.2 非目标（本版本不含）
- 多租户 / 账号体系（当前 userId 由 `prisma.user.findFirst()`/`upsert` 动态取，非硬编码；Auth（身份认证）为后续扩展）。
- 自主 Agent（智能体）式动态规划；本系统采用**预定路径工作流（Workflow）**，刻意追求可控。

### 1.3 技术约束
- 部署目标 Vercel（Serverless（无服务器）），单函数墙钟上限约 300s，要求任何环路必须有**硬终止上限**。
- LLM 供应商为 DeepSeek（深度求索），经 OpenAI 兼容协议接入，模型 `deepseek-v4-flash`。
- 数据库为 Neon Postgres（云托管 PostgreSQL），本地与线上共用同一云库。

## 2. 系统架构

### 2.1 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│ 浏览器（客户端）                                                │
│  · 题目列表 / 搜索 / 收藏 / 标签管理（React 组件）                │
│  · AI 出题页：fetch 读取 SSE 进度，按 phase 渲染进度条           │
│  · TanStack Query 管理查询缓存；useActionState 处理表单         │
└───────────────┬───────────────────────────┬───────────────────┘
                │ Server Actions            │ HTTP (SSE)
                ▼                           ▼
┌───────────────────────────┐   ┌──────────────────────────────────┐
│ 服务端动作层（Server Actions）│   │ API 路由层（Route Handlers）         │
│ questions.ts / tags.ts      │   │ /api/ai/generate (SSE 流式)         │
│ 直接 prisma 增删改 + 校验     │   │ /api/ai/workflow-test (验证用)       │
└───────────────┬────────────┘   └───────────────┬──────────────────┘
                │                                  │
                ▼                                  ▼
┌─────────────────────────────────────────────────────────────┐
│ 数据访问层（Prisma 单例） + AI 工作流编排层（LangGraph）         │
│  · workflow.ts：StateGraph 编排（分析→路由→规划→出题→校验→精炼环）│
│  · validator.ts / recordRun.ts / logger.ts                    │
└───────────────┬───────────────────────────┬───────────────────┘
                │                            │
                ▼                            ▼
        ┌──────────────┐          ┌────────────────────┐
        │ Neon Postgres │          │ DeepSeek (LLM)       │
        │ 5 张表         │          │ 简历分析/策略/出题    │
        └──────────────┘          └────────────────────┘
```

### 2.2 关键架构决策
- **App Router + Server Actions + Route Handlers 混合**：题库 CRUD（增删改）走 Server Actions（Next.js 自动生成 POST 端点、自动序列化），AI 流式生成走 Route Handler（需要 SSE（Server-Sent Events / 服务端推送事件）流式响应，Server Action 不适合长流）。
- **AI 编排与业务 CRUD 解耦**：AI 出题是独立子系统（`src/lib/ai/`），通过 API 触发，产出题目后由前端/现有保存逻辑写入题库，不直接耦合题库写操作。

| GitHub Actions | CI（持续集成） | push/PR 自动 type-check + test + build 三道闸门 |

## 5. 关键设计决策（核心）

每个决策按「问题 → 方案 → 实现位置 → 权衡」展开。

### 5.1 AI 工作流编排模型（LangGraph StateGraph）
- **问题**：出题涉及多步 LLM 调用 + 质量门禁 + 自我修正，普通线性函数难以表达「校验不达标→回退重出」的环。
- **方案**：用 `StateGraph` 定义 5 个节点与边，校验节点通过**条件边**回退到出题节点形成精炼环。
- **实现**（`workflow.ts` `buildWorkflow()`）：
  - 节点：`analyzeResume`（LLM，手写 for 循环重试 lastErr 回灌，非框架 `maxAttempts=3` + `timeout=300000`）→ `routeCandidate`（确定性，无重试）→ `planStrategy`（LLM，手写 for 循环重试，非框架）→ `generateQuestions`（手写域级重试）→ `validateQuestions`（确定性，无重试）→ END。
  - 条件边：`validateQuestions` → `shouldRefine` → `refine: generateQuestions` / `end: END`。
  - 状态用 `Annotation.Root`，含 `resume/jd/analysis/strategy/questions/failedDomains/callFailedDomains/logs/runId/generationDone/round/refineDomains/routing`。
- **权衡**：StateGraph 比手写状态机表达力强，但引入框架依赖；其 `stream()` 原生支持逐节点进度推送，是选它的主因。

### 5.2 确定性路由分流（为何不调 LLM 重分类）
- **问题**：出题前需确定「考谁、怎么考」（水平/角色/题型权重），能否交给 LLM 再分类？
- **方案**：用纯函数 `computeRouting(analysis)` 做分类，**刻意不调 LLM**。
- **实现**（`workflow.ts`）：
  - 输入是节点①已产出的结构化 `analysis`（含 `overallLevel` / `skills`），属结构化、现成数据。
  - 输出 `{ level, targetRole, hasBlindSpots, bias{concept, deepDive} }`：`BACKEND_KEYWORDS` 命中→`fullstack`；`level`→基础权重（senior 偏 `deepDive=0.71`）；`hasBlindSpots` 信号注入节点③ 要求至少一道补缺题。
  - 结果注入节点③ prompt 的 `routingHint`，让策略偏重题型。
- **权衡 / 理由**：① 输入已结构化，无需「理解」；② 需**同输入必同输出**（可控可复现）；③ 省一次 token（令牌）往返；④ 避免 LLM 分类漂移/幻觉。本质是把「需可控环节从 LLM 拿回确定性代码」。

### 5.3 并行出题扇出与并发安全
- **问题**：多个知识域互相独立，串行出题尾延迟高；并行写日志会有竞态。
- **方案**：`generateQuestions` 用 `mapWithConcurrency(limit=5)` 限 5 路并发扇出（fan-out（扇出））；每个域在 `generateForDomain` 内写私有 `localLogs` 便签本，跑完按固定顺序合并。
- **实现**（`workflow.ts`）：
  - 域级重试在循环内 `for attempt<=MAX_ATTEMPTS(3)`，`catch` 返回 `{ ok:false }` 而非 `throw`——保证单域失败**不连坐**其他域，也不让整体崩。
  - 失败域进 `callFailedDomains`，不参与精炼环。
- **真实工程发现（诚实记录）**：5 路并发实测约 **3.8x 提速、零 429**（多次实测，并发额度已非瓶颈）；`MAX_CONCURRENCY` 从 3 路调到 5 路后收益稳定。结论：并行扇出在域级解耦下真实提速，且实现正确、可观测。

### 5.4 确定性语义校验替代 LLM 评委
- **问题**：如何判断生成的题「质量达标」？能否让 LLM 自己评分（LLM-as-Judge（模型自评））？
- **方案**：用确定性规则 `validateQuestionSemantics` 做硬门禁，**不靠 LLM 自评**。
- **实现**（`validator.ts`）：5 条 100% 可判定规则——难度 1-5、内容 ≥30 字、标签非空、含开放式词元（为什么/如何/说说…）、与候选人技能有词重叠（相关性）。违规题所属域进 `refineDomains`。
- **权衡**：LLM 自评有同族偏差、位置/冗长偏差、主观任务一致率 <60%，不适合做硬门禁；确定性规则可复现、可单测、零成本。

### 5.5 自我优化精炼环（粒度假隔离 + 硬上限）
- **问题**：校验不达标时，是全部重生成，还是只重出坏的？会不会死循环？
- **方案**：只重出 `refineDomains` 中的失败域，保留已通过的好题（`keepDomains`）；设 `MAX_REFINE_ROUNDS=2` 硬上限。
- **实现**（`workflow.ts`）：
  - 重出时 `hint` 注入「上一版为何不达标」，让题变聪明（自我优化实质）。
  - `shouldRefine`：`refineDomains.length>0 && round<=MAX_REFINE_ROUNDS` → 继续，否则 END。
  - 调用层失败（`callFailedDomains`）与语义失败（`refineDomains`）**区分记录**，避免历史已修好的域残留。
- **权衡**：只重出失败域 = 省 token（令牌）+ 降延迟 + 防 LLM 非确定性导致的「好题重跑变差」回归；硬上限既防死循环，也防超 Vercel 300s。

### 5.6 四层可观测性
- **L1 终端**：`logger.appendLog` 实时 `console.log`（带 runId（运行ID）前缀）。
- **L2 状态**：`logs` 数组随 state 流转，最终在接口返回可见。
- **L3 页面**：`generate/route.ts` 推 SSE 进度事件（`analyzeResume`/`routeCandidate`/`planStrategy`/`generateQuestions`/`refine`/`done`），前端进度条 + 琥珀条展示。
- **L4 数据库**：`recordRun.ts` 写 `GenerationRun` 表（状态/水平/计划域/产出数/失败域/轮次/完整日志），runId 串联 L1-L3。

### 5.7 失败隔离与韧性
- **写库不影响业务**：`recordGenerationRun` 内部 `try/catch` 吞掉所有异常，数据库抖动绝不影响用户拿到题目（生产级「观测不阻塞业务」纪律）。
- **域级失败隔离**：单域 3 次重试仍失败 → 进 `callFailedDomains` 跳过，不阻断其他域产出。
- **状态覆盖陷阱处理**：LangGraph state 默认覆盖非累加，题打内部标记 `_domain`，重出时 `filter` 掉失败域旧题再合并，避免「好题被覆盖」。

### 5.8 API Key 安全管理
- **问题**：用户自备 DeepSeek Key，不能明文存。
- **方案**：AES-256-GCM 加密后存 **httpOnly Cookie**；服务端用环境变量 `API_KEY_ENCRYPTION_SECRET`（32 字节 hex）解密。
- **实现**（`crypto.ts` + `client.ts`）：
  - 加密格式 `iv:authTag:ciphertext`，GCM 自带防篡改认证。
  - `createLLM()` 获取策略：① Cookie 解密成功→用之；② 解密失败（Key 过期/篡改）→ **直接失败不回退**（防降级攻击）；③ 无 Cookie→回退 `.env` 的 `DEEPSEEK_API_KEY`（开发环境）；④ 都无→抛错。

### 5.9 数据访问层（Prisma 单例 + 外部化）
- **单例**（`prisma.ts`）：实例挂 `globalThis`，开发热重载时复用同一连接，避免连接数耗尽。
- **外部化**（`next.config.ts`）：`serverExternalPackages: ['@prisma/client', '.prisma/client']`，防止 Prisma 被打包进 bundle 导致 SSR 运行时报 `did not initialize yet`。

### 5.10 SSE 流式进度
- **实现**（`generate/route.ts`）：`ReadableStream` + `graph.stream({ streamMode: "values" })`，每节点完成 yield 一次完整状态快照。
- **去重**：`emitted` Set 防重复推送；`generationDone` 精确判定节点④是否真跑完（区分「0 题」与「未跑」）；精炼事件按 `refine-${round}` 只推一次，避免重出刷屏。
- **收尾**：`finally` 前 `await recordGenerationRun(lastChunk)` 写 L4，写库失败不影响已推送的 `done`。

### 5.11 前端状态管理
- **TanStack Query**（`QueryProvider.tsx`）：用 `useState` 初始化**单例** `QueryClient`（避免每次重渲染新建导致缓存清空）；收藏查询（`useQuery`）与收藏变更失效（`useMutation` + `invalidateQueries`）统一托管。
- **useActionState + Server Actions**：`QuestionForm` 用 `useActionState` 接 `createQuestion`/`updateQuestion`，表单校验失败按字段标红（`FieldErrors`）。
- **SSE 消费**：AI 出题页用原生 `fetch` + `ReadableStream` 读 SSE，按 `phase` 更新进度与最终题目。

## 7. 接口与数据模型设计（设计意图）

### 7.1 数据模型设计意图
- **核心域**：`User` / `Question` / `Tag` / `QuestionTag`（题目-标签多对多，关联表 `onDelete: Cascade` 级联删）。
- **可观测性域**：`GenerationRun`（独立运行记录，与业务题库解耦；`runId @unique` 串联 L1-L3 日志；`failedDomains`/`callFailedCount`/`rounds`/`logs Json` 支持事后复盘）。
- **索引意图**：`QuestionTag` 双外键 + 复合主键；`GenerationRun` 对 `runId` 与 `createdAt` 建索引，支撑按时间复盘。

### 7.2 API 契约
| 端点 | 方法 | 用途 | 响应 |
|------|------|------|------|
| `/api/ai/generate` | POST | SSE 流式出题 | `text/event-stream`，事件 `phase`∈{analyzeResume,routeCandidate,planStrategy,generateQuestions,refine,done,error} |
| `/api/ai/workflow-test` | POST | 非流式全链路验证 | JSON：`{ ok, runId, analysis, routing, strategy, questions, failedDomains, round, logs }` |
| `createQuestion` / `updateQuestion` / `deleteQuestion` | Server Action | 题目增改删 | `QuestionActionState { error, fieldErrors?, ok? }` |
| `createTag` / `deleteTag` | Server Action | 标签增删 | `TagActionState { error, ok? }` |

**SSE 事件负载约定**：`{ phase, status, summary?, analysis?, routing?, strategy?, questions?, failedDomains?, round? }`。

## 8. 测试与持续集成策略

### 8.1 单测（Jest 30 + RTL 16 + jsdom）
- **翻译配置**（关键坑）：Babel 规则内嵌进 `jest.config.js` 并 `configFile: false`——**不能**在项目根建独立 `babel.config.js`（会逼 Next.js 从 SWC 切回 Babel，拖垮 `next build`）。
- **路径别名**：`moduleNameMapper` 把 `@/` 映射到 `src/`，对齐 `tsconfig`。
- **测试范围**（当前 11 套，全绿）：
  - 组件层：`QuestionForm` 渲染 + 交互（提交/校验标红）。
  - 工作流层：`computeRouting` 确定性（senior→frontend+bias、含后端技能→fullstack）；精炼环「收敛」（不达标域重出后达标）、「不死循环」（永远不达标→轮次上限停止）。

### 8.2 CI（GitHub Actions）
- **三道闸门**：`type-check` job（`tsc --noEmit` + `prisma generate`）+ `test` job（`npm test`）+ `build` job（`next build`）。触发分支 `main` / `dev`，PR 亦触发。
- **build job 已启用**：provider 切 Postgres 后 CI 通过 GitHub Secrets 的 `DATABASE_URL` 连 Neon 建库；Vercel 部署侧同样配 `DATABASE_URL` 做 build 验证。

## 9. 已知技术限制与权衡

- **单用户模型**：`userId` 由 `prisma.user.findFirst()`/`upsert` 动态取（非硬编码）；多用户需接入 Auth session（代码注释已预留扩展点）。
- **并行真实提速**：如 5.3 所述，5 路并发实测约 3.8x 提速、零 429；并发额度已非瓶颈。
- **build 验证路径**：CI 已启用 `build` job（配 `secrets.DATABASE_URL` 连 Neon）；Vercel 部署同样跑 build 验证。
- **SSE 中断恢复**：当前 `generate` 接口为一次性流式响应，未实现断点续跑（属后续可扩展方向，不影响当前可用性）。

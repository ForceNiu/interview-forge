> 版本：v1.0 · 基准：当前代码真实落地状态（以 Prisma schema / 路由 / 页面 / 已提交 commit 为准）
> 用途：项目功能全貌的权威说明，供复盘、面试讲述、后续迭代参考。

## 1. 引言（Introduction）

### 1.1 目的
本文档定义 Interview Forge 的功能范围与技术规格，覆盖从前端、服务端、数据库到部署与 AI（人工智能）工作流的全链路能力，作为功能清单与验收的基线。

### 1.2 范围（Scope）
Interview Forge 是一个**全栈面试题库管理平台**，包含：题目增删改查（CRUD）、标签多对多分类、搜索与收藏、服务端表单校验、TanStack Query 服务端状态管理、基于 LangGraph.js 编排的 AI 自动出题工作流、GitHub Actions CI（持续集成）与 Vercel CD（持续部署）、Jest + React Testing Library 组件测试。

### 1.3 术语表（Glossary）
- **CRUD**：Create / Read / Update / Delete（新增/查询/修改/删除）四项基础数据操作。
- **Server Actions（服务端动作）**：Next.js 内置机制，前端可直接调用运行在服务端的函数，无需手写 API（应用程序接口）Route。
- **Prisma**：TypeScript 友好的 ORM（对象关系映射）工具，负责数据库建模与查询。
- **Zod**：TypeScript 优先的 schema（模式）校验库，用于服务端输入校验。
- **TanStack Query**：服务端状态管理库，统一管理异步数据的加载/错误/缓存。
- **LangGraph.js**：基于图（Graph）的 LLM（大语言模型）工作流编排框架（原生 TypeScript SDK）。
- **SSE（Server-Sent Events / 服务端推送事件）**：服务端向客户端单向流式推送数据的 HTTP（超文本传输协议）技术。
- **CI / CD**：持续集成 / 持续部署，代码推送后自动检查并自动上线。
- **GenerationRun**：每次 AI 出题运行的留痕记录（L4 可观测性）。

## 2. 总体描述（Overall Description）

### 2.1 产品前景（Product Perspective）
系统采用 Next.js App Router 单体全栈架构：前端（React 19）与后端（Server Actions / Route Handler）同仓库同进程，数据持久化于 Neon Postgres（云端 PostgreSQL），AI 出题由 LangGraph.js 编排、DeepSeek LLM（深度求索大语言模型）驱动。

### 2.2 用户特征
使用者为需管理面试题库、并希望基于简历自动生成定制化题目的开发者/面试官。具备基本前端使用能力，关注题目结构化与出题效率。

### 2.3 运行环境
- 本地：`npm run dev`，连接本地或云端数据库，需 `DEEPSEEK_API_KEY` 环境变量（AI 功能）。
- 生产：Vercel 托管，自动部署，环境变量 `DATABASE_URL` 指向 Neon Postgres。

### 2.4 设计与实现约束
- 语言：TypeScript（strict 严格模式）。
- 样式：Tailwind CSS v4 原子化（静态样式走 Tailwind 类，运行时算出的尺寸/颜色走 inline style（内联样式））。
- 数据库单例：`src/lib/prisma.ts` 用 `globalThis` 防热重载耗尽连接；`next.config.ts` 须 `serverExternalPackages` 含 Prisma。
- AI 编排：`@langchain/langgraph` 锁 v6 兼容版本，StateGraph（状态图）声明式构图。

### 2.5 假设与依赖
- 依赖外部 DeepSeek LLM API 可用性与并发额度。
- 依赖 Neon Postgres 网络连接（本地开发亦需联网）。
- Node 22 运行环境。

## 3. 功能需求（Functional Requirements）

> 每条需求含：描述 / 输入与前置 / 处理逻辑 / 输出与后置 / 优先级 / 验收标准。

### 3.1 题库核心管理（Question CRUD）

**FR-1.1 题目新增**
- 描述：填写标题、Markdown 正文、难度（1-5）、来源、关联项目，提交入库。
- 输入：`QuestionForm` 表单字段（经 Zod 校验）。
- 处理逻辑：`createQuestion` Server Action → `prisma.question.create` → `revalidatePath` → `redirect` 回首页。
- 输出：新题目出现在题库列表。
- 优先级：P0。
- 验收：提交合法表单后首页出现新卡片；空白标题被拦截。

**FR-1.2 题目编辑**
- 描述：复用 `QuestionForm`，预填已有数据，提交更新。
- 输入：题目 id + 表单字段。
- 处理逻辑：`updateQuestion.bind(null, id)` → Zod 校验 → `prisma.question.update` → `revalidatePath` 首页与详情。
- 输出：详情/列表刷新为最新值。
- 优先级：P0。
- 验收：编辑后数据与提交一致；非法值被拦截。

**FR-1.3 题目删除（事务级联）**
- 描述：确认后删除题目，并显式先删中间表再删题目，避免脏数据。
- 输入：题目 id。
- 处理逻辑：`DeleteButton`（`window.confirm` 确认）→ `deleteQuestion` Server Action → `prisma.$transaction` 先删 `QuestionTag` 再删 `Question` → `revalidatePath`。
- 输出：题目从列表与详情消失。
- 优先级：P0。
- 验收：删除后关联的中间表记录同步清理，无外键残留。

**FR-1.4 题目详情查看**
- 描述：动态路由 `[id]` 展示单题完整信息与嵌套标签。
- 输入：题目 id。
- 处理逻辑：Server Component `findUnique({ include: { tags: ... } })`。
- 输出：详情页渲染标题/正文/难度/标签。
- 优先级：P1。
- 验收：标签正确嵌套展示。

**FR-1.5 题库列表展示**
- 描述：首页卡片化列表，难度以色块区分。
- 输入：无（或服务端查询全部）。
- 处理逻辑：`findMany({ include: tags })`，按 `favorite` / 难度着色。
- 输出：卡片列表。
- 优先级：P1。
- 验收：列表加载即见全部题目与难度色。

### 3.2 标签与多对多分类（Tag）

**FR-2.1 标签 CRUD**
- 描述：独立标签管理页，支持新建（含颜色）与删除。
- 输入：标签名、颜色。
- 处理逻辑：`createTag` / `deleteTag` Server Action。
- 输出：标签列表更新。
- 优先级：P1。
- 验收：新建标签即时出现在列表；删除后不再可选。

**FR-2.2 题目关联多标签**
- 描述：题目表单多选标签，提交时建立多对多关联。
- 输入：`tagIds[]`。
- 处理逻辑：`tags: { set: tagIds.map(id => ({ id })) }`（先断旧再连新）。
- 输出：题目带多个标签，列表/详情可见。
- 优先级：P1。
- 验收：编辑题目切换标签后，旧关联被正确替换。

### 3.3 搜索与收藏（Search & Favorite）

**FR-3.1 前端实时搜索过滤**
- 描述：列表页输入关键词，客户端实时过滤题目（标题/内容）。
- 输入：搜索关键词（客户端状态）。
- 处理逻辑：`useState` + `.filter` 客户端过滤；搜索词属客户端状态，不进 TanStack Query。
- 输出：列表按关键词收窄。
- 优先级：P2。
- 验收：输入即过滤，无网络往返。

**FR-3.2 题目收藏**
- 描述：标记/取消收藏题目，独立收藏页查看。
- 输入：题目 id。
- 处理逻辑：`/api/questions/[id]/favorite` Route → 切换 `question.favorite` → 前端 `invalidateQueries` 刷新。
- 输出：收藏状态切换，收藏页同步。
- 优先级：P2。
- 验收：收藏页仅含 `favorite=true` 题目。

### 3.4 表单提交与服务端校验（Server Actions + Zod）

**FR-4.1 服务端 Zod 校验**
- 描述：所有写操作经 Zod schema 服务端校验，结构化返回字段错误。
- 输入：`FormData` 解析后的字段。
- 处理逻辑：`questionSchema.safeParse` → 失败 `return { ok:false, fieldErrors }`，不抛异常。
- 输出：表单渲染红色字段错误。
- 优先级：P0。
- 验收：绕过客户端直接 POST 仍被服务端拦截（最后一道防线）。

**FR-4.2 useActionState 表单绑定**
- 描述：React 19 `useActionState` 管理提交态与错误态，提交中不重复提交（`isPending`）。
- 优先级：P1。
- 验收：提交中按钮禁用；错误回显不丢输入。

### 3.5 服务端状态管理（TanStack Query）

**FR-5.1 收藏查询与缓存**
- 描述：收藏列表走 `useQuery`，统一 loading / error / 缓存。
- 输入：`queryKey: ['favorites']`。
- 处理逻辑：收藏页 `useQuery` 封装 `fetchFavorites`。
- 输出：组件不再手写三个 `useState`。
- 优先级：P1。
- 验收：刷新无闪烁；缓存命中不重复请求。

**FR-5.2 收藏变更自动失效刷新**
- 描述：收藏切换走 `useMutation`，成功后 `invalidateQueries` 自动重拉。
- 优先级：P1。
- 验收：切换收藏后列表自动更新，无需手动刷新。

### 3.6 AI 出题工作流（LangGraph.js 编排）

**FR-6.1 简历与岗位分析**
- 描述：输入简历文本 + 可选 JD（职位描述），LLM 分析产出候选人能力画像。
- 输入：`{ resume, jd }`。
- 处理逻辑：节点① `analyzeResume`（LLM）→ `analysis { skills, overallLevel, skillCategoryMap, blindSpots }`。
- 输出：结构化能力画像，供下游消费。
- 优先级：P1。
- 验收：返回 skills 非空、overallLevel 在 junior/senior 等区间。

**FR-6.2 确定性路由分流**
- 描述：基于分析产出"怎么考"的决策，刻意不调 LLM，保证可控可复现。
- 输入：`analysis`。
- 处理逻辑：节点② `routeCandidate` → 纯函数 `computeRouting` 算出 `{ level, targetRole, hasBlindSpots, bias{concept, deepDive} }`（含后端技能→fullstack、资深偏深挖、hasBlindSpots 信号注入节点③要求至少一道补缺题）。
- 输出：路由决策注入节点③ prompt。
- 优先级：P1。
- 验收：同简历必得同路由（确定性、零 LLM 调用）。

**FR-6.3 出题策略规划**
- 描述：LLM 基于路由偏重，规划要考的知识域与题量。
- 输入：`analysis` + 路由偏重提示。
- 处理逻辑：节点③ `planStrategy`（LLM）→ `strategy.domains[]`。
- 输出：知识域清单。
- 优先级：P1。
- 验收：资深简历产出更多 `project-deep-dive` 域。

**FR-6.4 并行出题（扇出）**
- 描述：各知识域互相独立，同时调用 LLM，缩短尾延迟。
- 输入：计划出的知识域。
- 处理逻辑：节点④ `generateQuestions` → `mapWithConcurrency(domains, 5, generateForDomain)`，域级失败隔离（单域失败进 `callFailedDomains`，不整体崩溃）。
- 输出：各域题目合并。
- 优先级：P2。
- 验收：多域日志时间戳同毫秒（真并发）；单域失败不影响其他域。

**FR-6.5 确定性质量校验**
- 描述：用硬规则卡质量，不依赖 LLM 自评（避免不可靠的同族评委偏差）。
- 输入：生成的题目 + 简历文本。
- 处理逻辑：节点⑤ `validateQuestions` → `validateQuestionSemantics`（难度 1-5 / 内容≥30 字 / 标签非空 / 含开放式词元 / 与简历相关）。
- 输出：达标题保留，不达标域进入精炼。
- 优先级：P1。
- 验收：含封闭式问法或短文本的题被判不达标。

**FR-6.6 自我优化精炼环**
- 描述：不达标只重出失败域（粒度隔离、不连坐），带硬轮次上限防死循环。
- 输入：不达标域 + 优化提示。
- 处理逻辑：条件边 `shouldRefine` → 回节点④只重出失败域（`MAX_REFINE_ROUNDS=2` 上限）→ 重新校验。
- 输出：达标后进入 END。
- 优先级：P1。
- 验收：第 1 轮不达标域在第 2 轮收敛为 0；永不达标时到第 3 轮停止、记录失败域。

**FR-6.7 SSE 流式进度推送**
- 描述：出题过程向前端实时推送阶段进度（分析/路由/规划/生成/精炼/完成）。
- 输入：工作流运行。
- 处理逻辑：`/api/ai/generate` Route Handler 以 `text/event-stream` 推 `phase` 事件。
- 输出：前端进度条 + 琥珀条展示。
- 优先级：P1。
- 验收：前端按阶段递进显示，不卡白屏。

**FR-6.8 运行留痕（L4 可观测性）**
- 描述：每次出题运行写入 `GenerationRun` 表，供复盘。
- 输入：运行结束状态。
- 处理逻辑：`recordGenerationRun`（try/catch 隔离，写库失败不阻塞主流程）→ `prisma.generationRun.create`。
- 输出：数据库留存状态/失败域/轮次/完整日志。
- 优先级：P2。
- 验收：每次运行在库中产生一条记录；写库异常不影响用户拿到题目。

### 3.7 工程化与部署（CI / CD）

**FR-7.1 持续集成闸门**
- 描述：`git push` 触发 GitHub Actions 自动 type-check（类型检查）+ 测试。
- 输入：代码推送（main / dev 双分支）。
- 处理逻辑：`.github/workflows/ci.yml` → `npm ci` → `prisma generate` → `tsc --noEmit` → `npm test`。
- 输出：CI 绿/红。
- 优先级：P0。
- 验收：类型错误或测试失败则 CI 红，阻止合并。

**FR-7.2 持续部署**
- 描述：推送后 Vercel 自动构建并部署到公网，HTTPS 自带。
- 输入：推送 main。
- 处理逻辑：Vercel 关联 GitHub → `build` → 部署。
- 输出：生产 URL 可访问。
- 优先级：P0。
- 验收：部署成功，全功能线上可用。

### 3.8 自动化测试（Jest + RTL）

**FR-8.1 组件单元测试**
- 描述：`QuestionForm` 与列表页的行为测试，CI 中运行。
- 输入：组件渲染。
- 处理逻辑：`jest.mock` 拦截 Server Action；断言可见行为与调用参数。
- 输出：测试通过/失败。
- 优先级：P1。
- 验收：空白表单 → 见"标题不能为空"；合法提交 → Action 被调用且参数正确。

**FR-8.2 工作流单测**
- 描述：覆盖精炼环收敛、不死循环、路由确定性分类等。
- 优先级：P1。
- 验收：11 个测试套件全绿（含重出收敛与轮次上限终止）。

## 4. 非功能需求（Non-Functional Requirements）

### 4.1 性能（Performance）
- AI 出题 5 路并发实测约 3.8x 提速、零 429（多次实测，并发额度已非瓶颈），实现正确且可观测。

### 4.2 安全（Security）
- AI API Key 仅存服务端环境变量（`DEEPSEEK_API_KEY`），不暴露前端。
- 写操作经服务端 Zod 校验，绕过客户端亦被拦截。
- `.env` 不进 git。

### 4.3 可用性（Usability）
- 表单提交中有 `isPending` 禁用态；列表加载有 spinner；错误有提示。
- AI 出题有实时进度条，避免白屏等待。

### 4.4 兼容性（Compatibility）
- 现代浏览器；SSE 为单向流，无需特殊协议支持。

### 4.5 可维护性（Maintainability）
- 状态图声明式构图，节点职责单一；确定性逻辑（路由/校验）与 LLM 节点分离，便于单测。
- 「需可控环节从 LLM 拿回确定性代码」贯穿设计。

### 4.6 可观测性（Observability）
- 四层：L1 终端 console / L2 state.logs / L3 页面琥珀条 SSE / L4 `GenerationRun` 数据库历史表。

## 5. 数据需求（Data Requirements）

### 5.1 数据模型（Data Model）
数据库：PostgreSQL（Neon）。共 5 张表：

**User（用户）**
| 字段 | 类型 | 说明 |
|------|------|------|
| id | String (cuid) | 主键 |
| email | String @unique | 唯一 |
| name / image | String? | 可选 |
| questions | 关联 | 一对多 |

**Question（题目）**
| 字段 | 类型 | 说明 |
|------|------|------|
| id | String (cuid) | 主键 |
| title | String | 标题 |
| content | String | Markdown 正文 |
| difficulty | Int (1-5) | 难度 |
| source | String | 来源：mock / jd / manual / other |
| projectHook | String? | 关联项目名 |
| isAiGenerated | Boolean | 是否 AI 生成 |
| favorite | Boolean | 是否收藏 |
| userId | String | 归属用户 |
| tags | QuestionTag[] | 多对多标签 |

**Tag（标签）**
| 字段 | 类型 | 说明 |
|------|------|------|
| id | String (cuid) | 主键 |
| name | String @unique | 标签名 |
| color | String | 颜色 |

**QuestionTag（题目-标签关联，多对多）**
| 字段 | 类型 | 说明 |
|------|------|------|
| questionId / tagId | String | 联合主键，双边 `onDelete: Cascade` |


**GenerationRun（AI 出题运行留痕）**
| 字段 | 类型 | 说明 |
|------|------|------|
| id | String (cuid) | 主键 |
| runId | String @unique | 与 L1/L2 日志串联 |
| status | String | "success" / "partial" |
| resumeLevel | String? | 候选人水平 |
| plannedDomains | String[] | 计划知识域 |
| producedCount | Int | 产出题数 |
| failedDomains | String[] | 最终失败域 |
| callFailedCount | Int | 调用层失败数 |
| rounds | Int | 精炼轮次 |
| logs | Json | L2 日志全量 |
| createdAt | DateTime | 创建时间 |

### 5.2 存储与保留
- 生产数据存 Neon Postgres；本地开发可连同一云库（需联网）。
- `GenerationRun` 记录长期留存，供复盘与成本分析。

## 6. 接口需求（Interface Requirements）

### 6.1 外部 API 路由（API Routes）
| 路径 | 方法 | 用途 |
|------|------|------|

## 9. 未来扩展（非当前范围 / Backlog）

### 9.1 多模态输入：简历文件与岗位 JD 图片

- **功能设想**：当前 FR-6.1 仅接受纯文本 `{ resume, jd }`。设想支持用户直接上传简历图片（PNG/JPG/截图）与岗位 JD 图片，系统自动提取文本后进入现有出题链路（不影响下游节点）。
- **当前落地（方案 C）**：`/ai-generate` 页面提示用户「请用任意工具将图片简历转为文字后粘贴」，不开发图片解析功能。现有 `analyzeResume` 及之后的路由/规划/出题/校验节点零改动。
- **技术约束**：DeepSeek 官方托管 API（V4 / chat / reasoner）为纯文本（text-only），**不支持图片像素输入**；要「看图」必须引入独立的 OCR（光学字符识别）/ 视觉（Vision）模型先把图片转为文本，再喂给现有 DeepSeek 文本链路。
- **候选方案（待评估，非当前范围）**：
  - **方案 A（前端 OCR（光学字符识别））**：浏览器内 `tesseract.js` 把图片转文字后填入 `resume` 字段，后端零改动；缺点：中文简历 OCR 准确率一般、排版/表格易乱，需实测。
  - **方案 B（第三方视觉 API）**：调用支持图片的视觉模型（如通义千问视觉版 / 智谱 GLM-4V）看图返回结构化文本；优点准确率高，缺点：新增模型依赖 + 新 API Key（应用程序接口密钥）+ 新成本 + 新错误处理。
  - **方案 C（当前采用）**：页面提示用户自行转为文字粘贴；零代码、零依赖。
- **影响评估**：属「旁路预处理器」，不动现有 LangGraph 工作流；新增难度集中在文件上传 / 大小类型校验 / 恶意文件安全 / 暂存与存储等工程边界，非算法复杂度。
- **优先级**：P3 / Backlog（对「增加面试机会」无加成，当前不做）。
